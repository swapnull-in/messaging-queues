The queue — ack, retry, dead-letter

A worker takes a message and the queue hides it for a visibility timeout. Ack in time → deleted. Crash/throw → it reappears and is retried (at-least-once). Fail too many times → it's moved to a dead-letter queue so it stops blocking others.

Produce jobs, then process — watch the poison job retry then dead-letter.

ready

dead-letter (max 3 attempts)

The proof: a healthy job is processed and acked (deleted). The poison job throws, so its visibility timeout lapses and it's redelivered — attempt 1, 2, 3 — then dead-lettered instead of blocking the queue forever. That redelivery is exactly what makes delivery at-least-once (and why consumers must be idempotent — next panel).

Idempotent consumers — effectively-once

At-least-once means the same message can arrive twice (a retry after a slow ack). If processing has a side effect — charge a card — a duplicate double-charges. An idempotency key + a processed-set makes reprocessing a no-op → effectively-once.

The proof: without dedup, two deliveries → $40 (double charge). With an idempotency key, the second delivery finds the key already processed and skips the side effect → $20, processed once. There's no exactly-once on the wire — you get effectively-once by making the consumer idempotent (dedup key, or a natural-key upsert).

Retries — exponential backoff & jitter

Retrying a transient failure immediately (or on a fixed schedule) makes every client retry in lockstep — a synchronized thundering herd. Exponential backoff spaces retries out; adding jitter de-synchronizes many clients so they don't all hammer the dependency at once.

Run with jitter off, then on — watch the retry spikes.
retries landing per 1s bucket · base delays 1s, 2s, 4s, 8s

The proof: plain exponential backoff still lands every client's retry at the same instant (1s, 2s, 4s…) — a spike that re-overloads the recovering dependency. Full jitter picks a random delay in [0, backoff], smearing the retries across the window so the load is flat. Always jitter.

Priority queues — urgent work first

A plain queue is FIFO. A priority queue serves higher-priority messages first, regardless of arrival order — so a password-reset email jumps ahead of a bulk newsletter. The risk: low-priority work can starve if high-priority never drains.

Enqueue a mix, then process — highest priority leaves first.

queue (sorted by priority)

processed order

The proof: enqueue low, low, HIGH — the HIGH job is dequeued first even though it arrived last. Real brokers implement this with priority levels (RabbitMQ) or separate per-priority queues drained in order. Guard against starvation with aging or a reserved low-priority worker.

Rate limiting — the token bucket

A token bucket refills at a steady rate up to a burst capacity; each request spends a token, and requests with no token are throttled. It smooths bursts to a sustainable rate — the standard shape for API limits and outbound-call pacing.

The proof: the bucket absorbs an initial burst up to its capacity, then admits requests only as tokens refill — so a spiky arrival pattern is shaped to a steady sustainable rate; the excess is throttled (429, or delayed). Bigger capacity = burstier; higher refill = higher steady throughput.

Backpressure — a fast producer, a slow consumer

When producers outrun consumers, an unbounded queue grows forever (memory blowup, rising latency). Consumer lag is the signal. Three responses: block the producer (flow control), shed load (drop/429), or scale consumers until the downstream is the bottleneck.

Run each policy and watch the lag curve.
queue depth (lag) per tick

The proof: unbounded → lag climbs every tick without limit (an overload becomes an OOM crash). Bounded + block caps the buffer and pushes back on the producer — throughput settles at the consumer's rate. Shed drops the excess to keep lag and latency bounded (best when the source can't be slowed and stale work is worthless). Scaling consumers helps only until the shared DB is the bottleneck.

Pub/sub — fan-out, no retention

A queue delivers each message to one consumer. Pub/sub broadcasts each message to every subscriber. Classic pub/sub (Redis) is fire-and-forget — a subscriber that wasn't connected misses the message (no retention). That's the key contrast with a Kafka log.

Add a subscriber, publish, add another subscriber, publish again.

The proof: every currently-connected subscriber gets each published event (fan-out). But a subscriber added after a publish never sees the earlier events — classic pub/sub keeps no history. When you need late/replaying readers or many independent consumer groups over retained history, you want a log (Kafka), not pub/sub.

Exchanges — direct, fanout, topic routing

RabbitMQ publishes to an exchange, which routes to queues by their bindings. Direct matches the routing key exactly; fanout ignores it (broadcast); topic matches wildcard patterns (order.*, *.eu).

Pick an exchange type and a routing key, then publish.

The proof: direct delivers only to queues bound to the exact key; fanout ignores the key and hits every bound queue; topic matches patterns (order.* gets order.eu & order.us; *.eu gets order.eu & payment.eu). The exchange decouples publishers from the set of consumers — add a queue with a new binding without touching the publisher.

The log — partitions, offsets, consumer groups, replay

A Kafka topic is an append-only, retained log split into partitions (parallelism). A message's key picks its partition, so per-key order is preserved. Consumers track their own offset; reading doesn't delete, so you can add a new group or replay from the start any time.

Produce a few keyed messages, then consume and replay.

consumer group offsets

The proof: messages with the same key always land in the same partition, so their order is preserved (A's events stay ordered even as B's interleave across partitions). Each consumer group has its own offset — the "realtime" group advances as it reads, and a brand-new group can replay the whole retained log from offset 0. That's what a queue (which deletes on ack) can't do.

The dual-write bug → outbox → CDC

A service must change its DB and publish an event. Two separate steps means a crash between them leaves them disagreeing — the module's #1 pattern. The outbox writes the event in the same transaction; a relay publishes it. CDC tails the DB's change log instead.

The proof: dual-write commits the DB then 💥 crashes before publishing → order PAID, no event, permanently inconsistent. The outbox writes the event row in the same transaction, so a crash just delays delivery — the relay replays it. CDC tails the DB's change log and emits the event with no app-level outbox table. Both are at-least-once → dedupe by id for effectively-once.

Event sourcing — state is a fold of events

Store the events as the source of truth, not the current state. State is a left-fold over the log — so you can replay to rebuild it, time-travel to any past version (a free audit log), and snapshot to bound replay cost.

Add/remove items, then rebuild by replay and snapshot.

event log (source of truth)

derived state (cart)

The proof: each command appends an event; the current cart is a fold over the log — throw the state away and it rebuilds identically by replaying. Fold only the first k events for the state "as of" then (audit / time-travel). A snapshot at version k means a rebuild replays only events after k, bounding the cost for long-lived aggregates. The price: more storage, thinking in events not rows.

CQRS — split writes from reads

Separate the write model (commands, consistency) from purpose-built read models kept in sync by projecting events. One event stream can feed many differently-shaped views — at the cost of a read-lag window (eventual consistency).

Like a post, then immediately query — see the stale read, then convergence.

write model (events)

read models (projections)

The proof: a command emits an event; a projector updates the read models asynchronously, so a query issued immediately after the write is momentarily stale (the read-lag window), then converges. The same events feed two views — a per-post counter and a leaderboard — each shaped for its query. You can add a new read model later and backfill it by replaying (CQRS + event sourcing compose).
